| D47 | 2026-11-20 | Failed bearer attempts (SVC-7) are counted per client address, at the local sign-in limit of 5 failures per 15 minutes. The address is the host of the connection's remote address; `X-Forwarded-For` is not trusted. A request that presents a valid token (enabled account, not expired or revoked) always authenticates, whatever the address's failure count, and is not a failure. Only failed attempts are limited: once an address has 5 failures in the window, a further failed attempt answers 429 `rate_limited` with `Retry-After` instead of 401, and is not counted again. A failure is any presented `Bearer` token that is refused (malformed, unknown, wrong secret, expired, revoked, disabled or deleted account, or an id that is not canonical decimal); a request with no bearer header, a missing scope (403) and any token sent outside `/api/v1/integration/` are not failures. Every request does the same lookup and comparison before the limiter is consulted, and the 429 is one fixed body, so the limit gives no signal about whether a token id exists. The check and the recording are one step under one lock, and the address map is swept at most once a minute and capped at 10,000 addresses (a failure from a new address while the map is full of live ones is answered 429). Behind a reverse proxy, as `docs/deploying.md` requires, every caller shares the proxy's address and so one failure budget, but no valid caller can be locked out by it: the worst an attacker can do is turn other failed attempts into 429. **REVIEW**: behind a reverse proxy all callers share one failure budget. | Reuses the limiter as the design asks ("failed bearer attempts are rate-limited per client address"). Checking the limit before the token, as first built, let anyone behind the same proxy lock every integration out with five bad requests. Trusting a forwarding header without a configured proxy list would let any client pick its own address and escape the limit. With 256-bit secrets, limiting failures is what throttles guessing. | agent (orchestrator ruling on verification 62; not yet seen by the owner) |

A customer's service can report a weight per setup on its own route, `PUT /api/v1/integration/weights`, under its own scope, `weights:write`; Hourglass applies it within limits an admin sets, shows it wherever a price is shown, records its source on every charge, and falls back to the rate rules when no valid report exists. The owner decided: (a) the client computes the weight and Hourglass applies it; Hourglass computes nothing from memory, storage or any other raw figure; (b) the weight is a field of its own report on its own route with its own scope, not a reserved label and not part of the deployments report; (c) a reported weight may describe what a setup currently reserves, which amends "bill what a setup reserves, not what it consumes": the reserved amount may change over time and be reported; it should be provisioned size, not live utilisation, and Hourglass cannot check this; (d) a reported weight changes the debit and nothing else: the snapshot that pressure sources and metering policies receive keeps the admin's weight (override, rate rule or default); (e) a usable reported weight replaces the rate rules for that setup, including a rule of weight 0; the way to exempt a setup is the per-setup override; (f) a report is accepted or refused as a whole; (g) a weight outside the admin's limits is refused, never clamped; (h) there is a minimum as well as a maximum, default minimum 0; (i) the switch and the limits are admin settings in the database, audited, not the config file; (j) an expired or missing weight falls back to the rate rules and does not fail the poll, unlike the deployments and pressure reports; (k) a setup left out of the report is charged at the fallback weight whatever its state, including the last interval of a release; the product does not remember a removed weight; (l) admins can see a refused report and how many stored weights the limits exclude; (m) with the feature off the route answers 409 `not_configured`, naming the admin setting; (n) the change is backward compatible: off by default, no configuration change after upgrade, and no route, parameter or response field removed.
