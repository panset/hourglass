| D47 | 2026-11-20 | Failed bearer attempts (SVC-7) are counted per client address, at the local sign-in limit of 5 failures per 15 minutes. The address is the host of the connection's remote address; `X-Forwarded-For` is not trusted. A request that presents a valid token (enabled account, not expired or revoked) always authenticates, whatever the address's failure count, and is not a failure. Only failed attempts are limited: once an address has 5 failures in the window, a further failed attempt answers 429 `rate_limited` with `Retry-After` instead of 401, and is not counted again. A failure is any presented `Bearer` token that is refused (malformed, unknown, wrong secret, expired, revoked, disabled or deleted account, or an id that is not canonical decimal); a request with no bearer header, a missing scope (403) and any token sent outside `/api/v1/integration/` are not failures. The check and the recording are one step under one lock, and the address map is swept at most once a minute and capped at 10,000 addresses (a failure from a new address while the map is full of live ones is answered 429). Behind a reverse proxy, as `docs/deploying.md` requires, every caller shares the proxy's address and so one failure budget, but no valid caller can be locked out by it: the worst an attacker can do is turn other failed attempts into 429. **REVIEW**: behind a reverse proxy all callers share one failure budget. | Reuses the limiter as the design asks ("failed bearer attempts are rate-limited per client address"). Trusting a forwarding header without a configured proxy list would let any client pick its own address and escape the limit. With 256-bit secrets, limiting failures is what throttles guessing. | agent (orchestrator ruling on verification 62; not yet seen by the owner) |
