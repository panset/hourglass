| D47 | 2026-11-20 | Failed bearer attempts (SVC-7) are counted per client address, at the local sign-in limit of 5 failures per 15 minutes. The address is the host of the connection's remote address; `X-Forwarded-For` is not trusted. A request that presents a valid token (enabled account, not expired or revoked) always authenticates, whatever the address's failure count, and is not a failure. Only failed attempts are limited: once an address has 5 failures in the window, a further failed attempt answers 429 `rate_limited` with `Retry-After` instead of 401, and is not counted again. A failure is any presented `Bearer` token that is refused (malformed, unknown, wrong secret, expired, revoked, disabled or deleted account, or an id that is not canonical decimal); a request with no bearer header, a missing scope (403) and any token sent outside `/api/v1/integration/` are not failures. Every request does the same lookup and comparison before the limiter is consulted, and the 429 is one fixed body, so the limit gives no signal about whether a token id exists. The check and the recording are one step under one lock, and the address map is swept at most once a minute and capped at 10,000 addresses (a failure from a new address while the map is full of live ones is answered 429). Behind a reverse proxy, as `docs/deploying.md` requires, every caller shares the proxy's address and so one failure budget, but no valid caller can be locked out by it: the worst an attacker can do is turn other failed attempts into 429. | Reuses the limiter as the design asks ("failed bearer attempts are rate-limited per client address"). Checking the limit before the token, as first built, let anyone behind the same proxy lock every integration out with five bad requests. Trusting a forwarding header without a configured proxy list would let any client pick its own address and escape the limit. With 256-bit secrets, limiting failures is what throttles guessing. | owner (ruling on verification 62) |
| D48 | 2026-11-20 | Service-account admin input: `name` is 1 to 64 letters, digits, `.`, `_` or `-`, starting with a letter or digit, unique (409 `conflict`) and not changeable; `description` is optional on create, at most 500 characters, trimmed; `scopes` is required (may be empty), an unknown scope is 400 `validation` with `field` `scopes`, duplicates are dropped and scopes are returned in the design's order. A new account is enabled and has no token. `PUT` replaces `description`, `scopes` and `enabled`, all three required. The issue body is optional; `expires_at`, if given, must be in the future (400 `validation`). The token secret is 32 random bytes as lower-case hex, so a token is `hgsa_<id>_<64 hex>`; the stored hash is hex SHA-256 of the secret. Audit actions: `service_account.create`, `.update`, `.delete`, `.token_issue`, `.token_revoke`, target `service_account:<id>`; the account snapshot is name, description, scopes and enabled, and the token entries hold only the token id and expiry. | The design leaves these open; each is the simplest rule that keeps names safe as text on holds and audit rows (SVC-4, SVC-6). | agent |
