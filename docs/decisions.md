# Decisions

Choices made where the spec is silent, plus spike results. Newest last.
Each entry: date, decision, why, who decided. Entries marked **REVIEW** are
the ones the project owner should look at.

|---|---|---|---|---|
| D1 | 2026-11-19 | Spec open questions use the bracketed assumptions: React; role named `developer`; `vsphere` pressure = highest of CPU, memory and storage allocation ratios across the clusters named in config; weights 1/2/4; a rejected user can be approved later. | Instructed by the owner. | owner |
| D2 | 2026-11-19 | `docs/SPEC.md` is a Markdown export of the source doc at revision 92. The one embedded architecture diagram is replaced by a text note. | The Markdown export cannot carry the drawing; the surrounding prose says the same thing. | agent |
| D3 | 2026-11-19 | Orchestration state (intent, plan, task briefs and results) is tracked in the repo under `.orchestrator/`; `docs/progress.md` is the human-readable status. **REVIEW**: say so if you would rather have `.orchestrator/` git-ignored. | The owner asked for state to be tracked in files in the repo. | agent |
| D4 | 2026-11-19 | Bazel is pinned to 7.4.1 in `.bazelversion`; rules_go 0.50.1, Gazelle 0.39.1. | 7.4.1 is the version installed on the development machine. | agent |
| D5 | 2026-11-19 | **Spike result (govmomi v0.56.2, Apache-2.0, needs Go 1.25 or newer).** The in-process simulator creates, nests, lists and destroys resource pools, including names like `lab-01_RP`. It reports static capacity figures (cluster totals, root pool `maxUsage`, datastore capacity and free space) but its allocation figures never move: `reservationUsed` and `usageSummary` stay 0 whatever pools, reservations or VMs are added. Details: `.orchestrator/hourglass-v1/tasks/01-vcsim-spike/RESULT.md`. | Required first technical task. | agent |
| D6 | 2026-11-19 | `vsphere` pressure ratios: CPU and memory = the cluster root resource pool's `runtime.{cpu,memory}.reservationUsed / maxUsage`; storage = `1 - sum(freeSpace) / sum(capacity)` over the cluster's accessible datastores; pressure = the highest of the three per cluster, then the highest across the clusters named in config. A zero capacity is an error, which fails the poll. **REVIEW**: this reads "allocation" as reservations, not live usage; first-run checklist item 3 covers checking it against a real vCenter. | The spec says "allocation ratios"; these properties are readable by a read-only account. | agent |
| D7 | 2026-11-19 | Test layers after the spike. Layer 3 (in-process simulator) asserts pool listing, nesting, name matching, orphans, appearance and disappearance of pools, and that pressure is in range with the storage ratio equal to the simulator's datastore figures. Layer 2 (hand-written fake) carries every pressure value: non-zero CPU and memory ratios, max-of-three, multi-cluster max, band crossing, zero-capacity guard. No vSphere logic loses coverage; only where it is asserted changes. | The simulator cannot move allocation figures (D5). | agent |
| D8 | 2026-11-19 | Layer 4 simulator container: the compose stacks use a small simulator image built from this repo (a test-only program that runs the govmomi simulator in-process and adds a control endpoint to create and destroy pools and to set the root pool's reservation figures), not the stock `vmware/vcsim` image. Product code gets no test-only override; the real `vsphere` provider and pressure source run unchanged against it. Fallback if setting the figures proves unworkable: the end-to-end test crosses a band by editing the band thresholds in Settings. **REVIEW**. | The acceptance path needs pressure driven across a band, which the stock image cannot do (D5); the stock image is also amd64-only. | agent |
| D9 | 2026-11-19 | The Bazel Go SDK and the `go` directive move from 1.24 to 1.25 or newer before the first dependency that needs it lands. | govmomi requires Go 1.25 (D5). | agent |
| D10 | 2026-11-19 | An `outages` table (`id`, `started_at`, `ended_at`, `reason`) is added to the spec's 15 tables. **REVIEW**. | MET-4 and ADM-4 require outages to be recorded and listed, and the data model has nowhere to keep them. | agent |
| D11 | 2026-11-19 | Band lower bounds are inclusive: exactly 50% gives 1x, 75% gives 2x, 90% gives 3x. **REVIEW**. | The spec says "90% and above"; the other rows are ambiguous at the edge. | agent |
| D12 | 2026-11-19 | A gap longer than twice the poll interval is not charged at all and is recorded as an outage; a gap of exactly twice the interval is charged in full. **REVIEW**: the other reading of MET-4 charges the first two intervals of a long gap. | "Longer gaps are not charged"; also "if the provider is unreachable, nobody is charged for the gap". | agent |
| D13 | 2026-11-19 | Selector values are unquoted tokens, so a label value containing a space or any of `, ( ) = !` can be stored (SET-3 allows any characters, up to 63, empty allowed) but cannot be named in a rule; it can still be matched by `key` / `!key`. `==` is accepted for `=`. **REVIEW**. | Simplest grammar that covers RULE-2; quoting is not in the spec. | agent |
| D14 | 2026-11-19 | Weights are written as plain decimals (`2`, `0.5`); signs, exponents, `inf` and `nan` are rejected. A stored rule with an unparseable selector or weight fails evaluation rather than being skipped. | RULE-1 "non-negative decimal"; the save path already rejects bad input (RULE-3). | agent |
| D15 | 2026-11-19 | `balance.low` fires when a balance goes from at least 10% of the allowance to below it, `balance.overdrawn` when it goes from above zero to zero or below; both can fire on one debit. With a zero allowance `balance.low` never fires. | "First drops below" / "first reaches" in the event table. | agent |
| D16 | 2026-11-19 | Projected run-out: a balance at or below zero shows as run out now; no burn in the last 24 hours shows no projection ("not this month"). | Dashboard pages: balance divided by average hourly burn over 24 hours. | agent |
| D17 | 2026-11-19 | After downtime across one or more month boundaries, each missed month is closed in order at startup, so debt carries through skipped months. Grants and resets need a non-blank reason; a reset that changes nothing is still written. | LED-3, LED-4, LED-5. | agent |
| D18 | 2026-11-19 | Two small core packages beyond the spec's suggested layout: `internal/settings` (typed admin settings, validation, resource-name template) and `internal/holds` (acquire and release rules), so that logic is testable without HTTP. | The layout is "suggested"; neither fits `internal/api` ("JSON handlers only"). | agent |
| D19 | 2026-11-19 | Charging starts at the poll where the policy first says to meter: that poll sets `metering_started_at` and debits nothing; each later poll debits the time since the previous successful poll. The time between the last poll and a release is not charged. **REVIEW**. | "Metering starts ... nothing is charged yet"; MET-4 charges poll to poll, and the collector is the only writer of debits. | agent |
| D20 | 2026-11-19 | "Last seen by the provider" and the allocations of the latest successful poll are kept in memory, not in the database. After a restart they are rebuilt by the poll that runs at startup; until it succeeds, release is not blocked by the teardown rule. | The data model has no column for them, and a restart already "loses at most one poll". | agent |
| D21 | 2026-11-19 | The month that needs closing is derived from the newest `allowance` entry in the ledger; no separate "current period" state is stored. | Keeps rollover idempotent with no schema addition (LED-3). | agent |
