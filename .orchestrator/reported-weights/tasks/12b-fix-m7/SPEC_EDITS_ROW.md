**Edits the source of `docs/SPEC.md` needs for D80.** `docs/SPEC.md` was not edited. Each item says what the spec text should become; D81 to D88 hold the details. (1) What is billed (Token system), first principle: replace it with: **Bill what a setup reserves, not what it consumes.** A held setup blocks a colleague whether it is busy or idle, so the charge depends on which setup you hold, for how long and what the setup reserves, never on live CPU or memory. What a setup reserves may change over time: a customer's own service may report a weight for it (provisioned size, not live utilisation, which Hourglass cannot check), and the weight follows what is reported. Billing still needs nothing from the infrastructure backend, and Hourglass never learns what a reported weight was computed from. (2) What is billed, second principle: after the sentence about the first matching rule add: A setup's weight comes from, in order, an admin's per-setup weight override, a usable reported weight, the first matching rate rule, and the default weight of 1. A reported weight is the client's own number, applied within limits an admin sets, and Hourglass computes nothing from memory, storage or any other raw figure. (3) Requirement RULE-1: add at the end: A rate rule sets a setup's weight only when the setup has no override and no usable reported weight. A usable reported weight replaces the rate rules for that setup, including a rule of weight 0; the way to make a setup free whatever is reported is a weight override of 0. (4) Requirement MET-2: add that the snapshot's `SetupState.Weight` is the base weight (the override, else the first matching rate rule, else the default), so a pressure source and a metering policy never see a reported weight and a weights report cannot move pressure or the multiplier. `pkg/hourglass/types.go` changes only the comment of that field. (5) Requirement MET-3: replace it with: For each hold the policy says to meter, the debit is `weight × multiplier × elapsed hours`, where weight is the policy's weight when it is above 0, else the resolved weight: the setup's override, else its usable reported weight, else the weight from the first matching rate rule, else the default. A poll charges the whole time since the previous successful poll at the weight resolved at that poll, with no pro-rating inside an interval, and a setup with no usable reported weight (none sent, expired, left out of the latest report, outside the limits or the feature off) is charged at its fallback weight in every state of the hold, including the poll that completes a pending release, without failing the poll. One usage sample and one ledger debit per metered hold are written in a single transaction with the pressure sample, and the sample records the weight and its source. (6) Data model, `usage_samples` row, columns: add `weight_source` (text, one of `override`, `reported`, `rule`, `default` or `policy`, null for a row written before migration 0008). Notes: `rule_selector` is set only when the source is `rule`, so it is null when the policy overrode the weight, when the default applied, and when an override or a report applied. (7) Data model, `setups` row, columns: add `weight_override` (real, null when none, finite, from 0 to 1e12, not bound by the reported limits). Notes: the override pins the setup's weight above a reported weight and the rate rules whether reported weights are on or off, belongs to the setup and survives a rename, and is part of the setup's audit snapshot only when set. (8) Data model, new `reported_weights_meta` row: the single-row table of the stored weights report, columns `observed_at`, `received_at` and `service_account` (the name of the account that sent it), replaced with the entries in one transaction and kept across restarts like the other report tables. (9) Data model, new `reported_weights` row: the entries of the stored weights report, columns `setup_name` (primary key, a name and not a foreign key, so a name that matches no setup is stored and the weight follows the name), `weight` (real) and `attributes_json` (text, default `{}`, stored and returned unchanged and never interpreted). (10) Data model, `settings` row, notes: add that the key `reported_weights` holds one object with `enabled` (default false, true only when `max` is set), `min` (default 0, finite, from 0 up to `max`), `max` (default null, or finite, above 0 and at most 1e12) and `max_age` (default `10m`, a duration from `1m` to `24h`), all four required when the key is present in a `PUT`, optional on `PUT` as a whole (a body without it leaves the stored value unchanged), always returned by `GET`, and audited with the whole object as the before and after value. (11) Requirement ADM-2: add `reported weights (switch, minimum, maximum, maximum age)` to the list of metering settings, and add that the maximum age should be at least twice the poll interval, which is advice and not a validation rule. Tightening the limits stops a stored weight outside them from applying at once and makes every later report that still holds one refuse whole; after the maximum age every setup is back on its fallback weight with polls succeeding. (12) Requirement ADM-4: add that the collector view shows, while reported weights are on, the last accepted weights report (observed time, received time, sending service account, how many weights it holds and how many of them the limits now exclude, names that match no setup included) and the last report refused with 400 (time, service account and message, kept in memory and lost at a restart).
