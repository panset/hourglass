# 02 Milestone 2: migration 0008, store queries, the weights report in `internal/reported`, the `reported_weights` setting
Job intent: .orchestrator/reported-weights/INTENT.md (read it first). Contract: .orchestrator/reported-weights/CONTRACT.md (binding).
## Goal
The storage and settings foundation of docs/design/reported-weights.md, with WGT-17 fully implemented and tested over HTTP. No resolver, no collector change, no report route, no reader change: those are later milestones and must not be started here.
## Build
1. Migration `0008` (design "Changes by area" and "Compatibility: Database"): tables `reported_weights_meta` (single row: `observed_at`, `received_at`, `service_account`) and `reported_weights` (`setup_name` primary key, `weight`, `attributes_json`), column `usage_samples.weight_source` (nullable text), column `setups.weight_override` (nullable). Additive only; no existing row rewritten. Follow CONTRIBUTING.md "Add a migration" (Gazelle, the migration-count and data-model store tests). Shape the single-row table like the existing report tables (D46).
2. `internal/store`: queries to replace and read the weights report (whole, atomic, like the deployments report); write and read `usage_samples.weight_source`; read and write `setups.weight_override`. Add the columns to the store's types so later milestones can use them, but leave every existing caller's behaviour unchanged (existing samples keep being written with a null source for now; milestone 3 sets it). Do not build the ledger weight aggregates (milestone 5).
3. `internal/reported`: submit and read the weights report with the shared ordering and clock-skew rules (design B1, B2 "Ordering and clock skew", B3 first bullet), independent of the deployments report's ordering. Value limits (minimum, maximum) and `max_age` come from the caller. The package validates what it stores, as D45 says it does for the other reports: setup name non-empty and not repeated, weight finite and within the caller's limits (inclusive; negative zero stored as 0), attributes within the limits of design B1. The entry-position error text required by B2 ("weights[3] (setup \"lab-03\"): weight 25 is above the maximum 20") should be produced by one function that the HTTP handler of milestone 4 can reuse; decide where it lives and say so. Also the in-memory "last refusal" record (time, account name, message) of design B2, with a setter and getter; milestone 4 calls it.
4. `internal/settings`: the `reported_weights` key (design D1): object `{enabled, min, max, max_age}`, defaults `false, 0, null, "10m"`, validation exactly as the D1 table, JSON form, audited like the other keys with the whole object as before and after value.
5. `GET` and `PUT /api/v1/admin/settings` (design D1 bullets, "What the code does today: Settings and setups"): `GET` always returns the key; on `PUT` the key is optional and a body without it leaves the stored value unchanged (take care: today an absent key is saved as its default); when present all four fields are required; it is not added to `settingsKeys` or to the schema's `required` list. Update `api/openapi.yaml` for the Settings schema and regenerate `ui/src/api/schema.gen.ts` (`cd ui && npm run gen:api`). If the regenerated type breaks UI type-checking or UI tests, make the smallest fixture fix under `ui/src` and list it; the Settings page UI itself is milestone 6.
## Tests (named after ids; each must fail when the requirement is broken)
- WGT-17, over HTTP: every row of the D1 table (each bound, each rejection, `enabled` true without `max`), all four fields required when the key is present, audit entry with before and after objects, a PUT with only the eight existing keys leaves a previously stored non-default `reported_weights` unchanged and still answers as v1.1.0 did, `GET` always returns the key.
- Store and `internal/reported` tests for the weights report: atomic replace, survives reopening the database (part of WGT-7; name them `TestWGT7_...`), stale / equal / more than 2 minutes ahead, independence from the deployments report's `observed_at`, validation of each entry rule (name them `TestWGT8_...`), unknown names stored. Migration test: a database at migration 0007 with rows upgrades and no existing row changes.
