# 10 pkg/hourglass: public extension API and registry
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
The public package `pkg/hourglass` that extension authors import: the four interfaces, the data types they exchange, the event list and the registry. Spec: docs/SPEC.md "Extension points" (the Go block is normative: reproduce those declarations exactly, names and signatures), EXT-1, EXT-2, and the data model for the mirrored structs. This is a public interface that third parties build against; favour a small, stable, well-documented surface.
## Contents
- `Setup`, `ResourceProvider`, `Allocation`, `PressureSource`, `MeteringPolicy`, `Decision`, `Hook`, `Event` exactly as in the spec.
- Types the spec leaves to "plain structs that mirror the data model": `User` (id, username, email, name, roles), `Hold` (id, setup name, user id, acquired/metering-started/deployed/released times, pointers where nullable), `Snapshot` (poll time; enabled setups each with labels, details, resolved weight and expected resource name; active holds; the provider's allocations for this poll; whether a provider is configured), `HoldState` (the hold, its setup with resolved weight, its user, and the matching allocation if the provider reports one). Give Snapshot small helper methods only where a pressure source or policy would otherwise have to re-implement matching (e.g. look up the allocation for a setup). Extensions need no database access.
- Event type constants for all eleven events in the spec's event table, `EventTypes()` returning them in table order, and `Vetoable(eventType string) bool` (only `hold.acquiring`).
- Factories: `ProviderFactory`, `PressureFactory`, `PolicyFactory`, `HookFactory`, each `func(config json.RawMessage) (T, error)`; the opaque config block arrives as JSON regardless of the config file's own format; a nil/empty block must be acceptable to factories that need no config.
- Registry in the style of `database/sql`: `RegisterProvider`, `RegisterPressureSource`, `RegisterMeteringPolicy`, `RegisterHook` (panic on empty name, nil factory or duplicate), plus lookups that build an instance by name: `NewProvider(name string, config json.RawMessage)`, `NewPressureSource`, `NewMeteringPolicy`, `NewHook`, each returning an error for an unknown name that lists the registered names sorted (EXT-2), and `Providers()`, `PressureSources()`, `MeteringPolicies()`, `Hooks()` returning sorted names. Safe for concurrent use.
- A `doc.go` package comment explaining the model in a few paragraphs, with a short example of registering an extension.
Not in this task: `Run()`, config-file loading, any concrete extension, fakes (next task). Do not import any `internal/` package or any non-stdlib module. The package must not mention vCenter/vSphere, sizes, or concrete extension names, except that doc comments may quote the spec's own generic wording.
## Tests
Registry behaviour (register, duplicate panic, unknown-name error text lists names, sorted listing, concurrent register/lookup under `-race`), event list matches the spec table, Snapshot helpers. Tests must not leak registrations between cases (provide an unexported reset or use unique names). Names cite `EXT-1` / `EXT-2`.
## Scope
