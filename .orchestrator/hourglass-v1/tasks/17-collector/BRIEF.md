# 17 internal/collector
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
Package `internal/collector`: the polling loop that builds the Snapshot, asks the extensions, and writes samples and debits. This is where money is charged; correctness, atomicity and idempotence matter more than anything else. Spec: docs/SPEC.md "Burn rate", "Lifecycle of a hold", MET-1..MET-6, HOLD-3, HOLD-4, ADM-4, "Rollout and calibration" third bullet, events `hold.metering_started`, `hold.deployed`, `poll.failed`; decisions D11, D12 in docs/decisions.md.

## Behaviour
`New(Deps) *Collector` with: store, provider (`hourglass.ResourceProvider`, may be nil), pressure source, metering policy, events emitter, ledger service, clock, logger.
`RunOnce(ctx) error`, one poll at time T = clock.Now():
1. Record a collector run start. Load settings, enabled setups with labels, rate rules, active holds with their users.
2. Resolve each setup's weight (first matching rate rule, else default weight) and expected resource name (`settings.ResourceName`).
3. If a provider is configured, `List` allocations (30 s timeout). Match allocations to setups by resource name. Duplicated resource names count once.
4. Build `hourglass.Snapshot` (enabled setups only: SET-5), then call the pressure source; a value outside [0,1] or non-finite is an error. Then call the policy for every active hold.
5. Any provider, pressure or policy error fails the whole poll: nothing is charged, no samples are written, the run is recorded as failed with the error, `poll.failed` is emitted, and RunOnce returns the error. A failed poll does not move "previous successful poll".
6. Smoothing: smoothed pressure = mean of the raw values of successful polls in the last 15 minutes including this one; multiplier from the bands.
7. Elapsed time: `metering.ChargeableElapsed(previous successful poll time, T, poll interval)`. If it reports an outage, record an outage row covering the gap and charge nothing this poll. The first poll after start with no previous successful poll charges nothing.
8. In ONE transaction: the pressure sample; for each hold the policy says to meter: if the hold's metering had not started, set `metering_started_at = T` and charge nothing this poll (a zero-debit sample is still written); otherwise debit = `metering.DebitMT(weight, multiplier, elapsed)`, where weight is the policy's override when > 0, else the rule weight, written as one usage sample (with the rule selector, or null when overridden or defaulted, plus pressure, multiplier and the policy's reason) and one ledger debit through the ledger service. The usage-sample insert is idempotent on (hold_id, T); when it reports "already present" the debit is skipped (MET-5). Zero debits write a sample but no ledger entry. Holds whose setup the provider reports for the first time get `deployed_at = T`. Orphans (allocations matching a setup's resource name while that setup has no active hold, including disabled setups) are upserted and stale ones removed; allocations matching no setup are ignored (HOLD-4). The run is marked successful.
9. After commit: emit `hold.metering_started`, `hold.deployed`, and the balance events returned by the ledger service. With no provider configured, deployed is never set (lifecycle step 3).
10. Shadow mode (`enforcement` off) changes nothing here: debits are still written (MET-6).
- State kept in memory after each successful poll for other packages: `LastPoll() PollView` with the poll time, the set of reported resource names, per-setup last-seen time, current raw/smoothed pressure and multiplier. `PollView.Reported(resourceName) bool`. Before the first successful poll, `LastPoll()` reports `OK=false`.
- `Run(ctx)`: polls immediately at start, then every poll interval (re-read from settings each cycle so an admin change applies from the next poll); also calls the ledger service's `RolloverDue` before each poll and prunes old rows once a day (usage samples older than 13 months, event deliveries older than 90 days, expired sessions). A panic in an extension is recovered and treated as a failed poll. Overlapping runs never happen.
- Rule and settings changes take effect from the next poll and are never retroactive (RULE-4, ADM-2): everything is read fresh each poll and past samples are never rewritten.
