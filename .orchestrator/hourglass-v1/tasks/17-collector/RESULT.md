## Transaction boundaries (one poll at T = clock.Now() truncated to ms, UTC)
1. Own autocommit write: `StartCollectorRun(T)`. Serialised by an in-process mutex (no overlapping RunOnce/prune).
2. Reads, outside any transaction: settings, all setups with labels, rate rules, active holds, users and roles, previous successful run (`LastSuccessfulRunBefore(T)`), pressure samples since T-15m.
3. Extension calls, outside any transaction, each with a 30 s timeout in its own goroutine with panic recovery: provider `List`, pressure `Pressure`, policy `Decide` per hold.
4. ONE `store.Tx`: pressure sample (if absent); outage row if the gap > 2x interval; per active hold (re-read with `GetHold` inside the tx; released holds skipped): `SetDeployed` if the provider reports it, `SetMeteringStarted` (start poll: zero debit) or debit computation, `InsertUsageSample` (idempotent; "already present" skips the debit), `Ledger.DebitTx` only for inserted samples with debit > 0; orphan upserts and `DeleteOrphansNotSeenSince(T)`; `FinishCollectorRun(ok=true)`. Any error rolls all of it back.
5. After commit: in-memory PollView swap, then events in order per hold (hold id ascending): `hold.metering_started`, `hold.deployed`, then that hold's `balance.low` / `balance.overdrawn`.
- Failure at any step: autocommit `FinishCollectorRun(ok=false, error)`, `poll.failed` with `Data{"error": msg}`, error returned; PollView unchanged and, because the run is not ok, "previous successful poll" does not move.
- `Run`: loop of `Ledger.RolloverDue` (error logged), `RunOnce`, daily prune (usage samples older than 13 months, event deliveries older than 90 days, expired sessions; each its own statement, errors logged), then wait `poll_interval` re-read from settings (default 5m if settings fail to load).

## Decisions for docs/decisions.md
1. "Previous successful poll" is read from `collector_runs` (newest ok run strictly before T), not memory: a restart within 2x interval charges the real gap (consistent with D20 "loses at most one poll"), and two collectors at the same T compute the same elapsed so MET-5's sample uniqueness alone prevents the double debit. Pressure sample insert is idempotent for the same reason, and a duplicate sample at T is not counted twice in smoothing.
2. `usage_samples.pressure` stores the smoothed pressure (the value the multiplier came from).
3. Outage polls and the first-ever poll still write zero-debit samples for metered holds (and can start metering); no ledger entry.
4. The 30 s timeout applies to pressure and policy calls too, not only the provider (spec gives no bound; keeps a hung extension from stalling metering). A call that ignores its context is abandoned.
5. A policy decision with a negative or non-finite weight fails the poll (conformance contract "weight is finite and not negative").
6. A stored rule that fails evaluation (D14) or a resource-name template error fails the whole poll; nobody is charged.
7. Hold rows are re-read inside the transaction; a hold released after the read phase is not charged, deployed or sampled (D19: time after the last poll before release is not charged).
8. Duplicated allocation names: first one wins; Snapshot.Allocations carries every distinct allocation (matched or not); orphan check is per resource name, skipped if any setup with that name has an active hold. Two setups resolving to the same resource name both see the allocation.
9. Orphans are cleared (`DeleteOrphansNotSeenSince(T)`) on every successful poll, also with no provider (then there are none).
10. Event order per hold: metering_started, deployed, balance events; holds in id order. Events go to `Deps.Events` (not the ledger service's emitter) so one queue keeps that order.
11. Prune runs on the first cycle after start and then every 24 h of clock time (in memory).
