# 21c API handlers: admin routes
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
Replace the 501 stubs in `internal/api/handlers_admin.go` with working handlers for: `GET /api/v1/admin/users?status=`, `PUT /api/v1/admin/users/{id}/roles`, `POST .../reject`, `POST .../grants`, `POST .../reset`, `POST /api/v1/admin/setups`, `PUT` and `DELETE /api/v1/admin/setups/{id}`, `GET`/`PUT /api/v1/admin/rules`, `GET`/`PUT /api/v1/admin/settings`, `GET /api/v1/admin/collector`, `GET /api/v1/admin/audit`. Spec: docs/SPEC.md "Roles and permissions" (table and the rules list, every bullet), SET-1..SET-6, RULE-1..RULE-4, LED-4, LED-5, ADM-1..ADM-5, AUTH-8, events `user.approved`.
## Notes
- Users list: every user with roles, status, balance, month-to-date burn, active holds; pending requests (oldest first) available via `status=pending`; overdrawn users first in the default listing; the pending count for the navigation is in the response as the OpenAPI defines.
- Roles (`PUT`): replaces the role set (valid roles: `developer`, `admin`). A non-empty set on a pending or rejected user approves them: status active, first allowance through the ledger service (at most once per period), `user.approved` emitted on the first role ever assigned. An empty set returns the user to unassigned (status stays active; they do not reappear as pending) and is refused with `has_active_hold` while they hold a setup. An admin cannot remove their own `admin` role (`self_demote`). The local admin's roles cannot be changed at all (`local_admin_protected`); nor can it be rejected, granted tokens or reset. All in one transaction with an audit row holding before and after.
- Reject: status `rejected`; the user leaves the pending list but can be given a role later.
- Grants / reset: through the ledger service; reason required; negative grants allowed.
- Setups: create, update (name, labels, details, enabled, resource_name_override), delete. Validate labels (SET-3), details is well-formed JSON of at most 256 KB stored and returned unmodified (SET-2: byte-for-byte as received after validation), unique name (`conflict`). A setup with an active hold cannot be deleted or disabled (`setup_held`). Deleting a setup with past holds: if the schema forbids it, refuse with `conflict` and a message telling the admin to disable it instead; record what you did.
- Rules: `GET` returns the ordered rate rules with per-rule first-match counts, the default weight and the setups falling through; `PUT` replaces the ordered list (and default weight if the OpenAPI carries it there), rejecting any invalid selector with `invalid_selector` and the parse error and position of the offending rule, and returns the new counts. Applies from the next poll (nothing to do: the collector reads fresh).
- Settings: `GET` returns the settings JSON plus the read-only runtime block (provider, pressure source, policy, hooks, OIDC issuer, timezone: names only); `PUT` validates through `internal/settings`, returning `validation` with the field name.
- Collector: active extension names, last successful poll, last error, recent runs, outages, orphans, recent failed event deliveries, queue length.
- Audit: every admin action above writes an audit row (actor, action, target, before, after) in the same transaction as the change (ADM-3); the list is newest first with actor and action filters and limit/offset. Use a small consistent action vocabulary (e.g. `user.roles`, `user.reject`, `ledger.grant`, `ledger.reset`, `setup.create`, `setup.update`, `setup.delete`, `rules.replace`, `settings.update`, `hold.force_release`) and list it in RESULT.md. Secrets never enter audit rows.

## Rules
- `internal/api` holds JSON handlers only: no HTML, no business rules that belong in `internal/holds`, `internal/ledger`, `internal/settings`, `internal/rules`. Handlers validate input, call those packages and the store, and shape responses.
- Every number comes from the backend (UI-1): compute derived values (cost per hour, projections, month-to-date burn, match counts) here or in the packages above, never leave them to the UI.
- Never return secrets. Never leak data in error bodies. Amounts in tokens (milli-tokens / 1000) as the OpenAPI says; timestamps RFC 3339 UTC.
- If the OpenAPI file is wrong or missing a field you need, do not edit it: implement the closest conforming behaviour and list the problem in RESULT.md. One exception already decided: the `expected_start_at` field under a setup/hold metering object is always null (the UI shows the policy reason text instead).
- Another agent is implementing the other handler file in the same package at the same time. Touch only your handler file, your own new files (prefix them `user_` or `admin_` as appropriate) and their tests; do not edit `router.go`, `helpers.go` or the other handler file. If you need a shared helper changed, add your own in your files and note it. A missing store query may be added only as a new file `internal/store/<task>_queries.go` with a test. No new dependencies; do not run gazelle on directories other than `internal/api` and `internal/store`, and expect the other agent to regenerate `internal/api/BUILD.bazel` too (re-run gazelle last thing before you finish).
- Tests: `httptest` against the real router with a real store in `t.TempDir()`, real services, fakes for extensions and a fake clock; sign in by creating sessions through `internal/auth` test helpers or the real endpoints. Names cite requirement ids. Each handler: success shape (assert the JSON fields), each error code it can return, and that a pending/unassigned user and an anonymous caller get 403 `no_role` / 401 with no data.
- Verify: `go test -race -count=1 ./internal/api/... ./internal/store/...`, `go build ./...`, `go vet ./internal/...`, both tools scripts. Run Bazel once at the end (`bazel test //internal/api/...`, allow 10 minutes); if it fails only because the other agent's file is mid-edit, say so.
