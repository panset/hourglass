# 33b e2e simulator tool (test-only vCenter stand-in with a control endpoint)
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
A small test-only Go program, `e2e/simulator` (binary name `hourglass-vcsim`), that the local compose stacks will run as "the simulator as a container" (docs/SPEC.md "Testing without a vCenter" item 4). It runs the govmomi simulator in-process and adds a control HTTP endpoint so the end-to-end test can create and destroy resource pools and drive the figures the `vsphere` pressure source reads. Decisions D5 and D8 in docs/decisions.md explain why the stock image cannot do this. This is test tooling, not product code: nothing outside `e2e/` may import it, and product code gets no test hooks.
## Context
tasks/01-vcsim-spike/RESULT.md (what the simulator models; mutating model objects was suggested but NOT tried: establishing that it works is the first thing to do), tasks/30-vsphere/RESULT.md (exactly which properties the adapter reads: the root resource pool's `runtime.cpu/memory.reservationUsed` and `maxUsage`, and datastore `summary.capacity`/`freeSpace`), `providers/vsphere` source.
## Requirements
- Flags/env: SOAP listen address (default `0.0.0.0:8989`, TLS with the simulator's self-signed certificate, as the real thing would be), control listen address (default `0.0.0.0:8990`, plain HTTP), username and password for the simulated vCenter (defaults `user` / `pass`, overridable; these are dummy values for a simulator), model size (1 datacenter, 1 cluster, a few hosts).
- Control API (JSON): `GET /healthz`; `GET /pools`; `POST /pools {"name": "lab-01_RP"}` (creates under the cluster's root pool; idempotent); `DELETE /pools/{name}`; `PUT /pressure {"cpu": 0.8, "memory": 0.2, "storage": 0.1}` which sets the root pool's reservationUsed for CPU and memory to that fraction of maxUsage and the datastores' free space to match the storage fraction (any omitted field unchanged); `GET /pressure` reporting the fractions currently readable through the API.
- The figures set through `PUT /pressure` must be visible through the real vSphere API surface the adapter uses (property collector reads), not just in memory. Prove it with a test that starts the tool's server in-process, connects the REAL `providers/vsphere` provider and pressure source to it (through the public registry with a config block), and asserts: pools created via the control API are listed by the provider; deleting removes them; setting cpu 0.8 makes the pressure source return 0.8 (max of three); raising storage above that wins; values survive repeated reads.
- If setting the root pool figures proves impossible through the simulator's object model, stop and report `blocked` with what you tried (the fallback in D8 is then used); do not fake it by bypassing the vSphere API.
- Graceful shutdown on SIGTERM. Structured log lines. No dependency beyond govmomi and the standard library.
- Every file has the SPDX line. `tools/check_core_generic.sh` must still pass (govmomi is allowed under `e2e/`).
## Scope
May write: `e2e/simulator/`, this task folder. BUILD via `bazel run //:gazelle -- e2e/simulator` plus the SPDX first line. No go.mod changes should be needed (govmomi is already a dependency); if `go mod tidy` wants to change go.mod/go.sum, apply only that. Other agents are editing `internal/api`, `ui/` and `cmd/` concurrently; Bazel commands queue.
## Done when
`go test -race -count=1 ./e2e/simulator/...` and `bazel test //e2e/simulator/...` pass (allow 15 minutes), `go build ./e2e/...` passes; RESULT.md documents the control API with curl examples and how the figures are set.
