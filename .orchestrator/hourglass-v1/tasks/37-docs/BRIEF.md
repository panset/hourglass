# 37 documentation: README quick start, extending, deploying, contributing
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
The four documents the spec requires (docs/SPEC.md "Repository files"): `README.md` with a quick start, `docs/extending.md` covering the four interfaces and the event list, `docs/deploying.md` covering bundled and split modes, and `CONTRIBUTING.md`. Readers: a developer or lab admin who has never seen the project. Everything stated must be true of the repository as it is: check commands by running them, and check names, flags, config keys and paths against the code, not against the spec or the briefs.
## Sources
Code and: `deploy/README.md`, `deploy/config.sample.yaml`, `deploy/seed.sample.yaml`, `examples/custom/README.md`, `pkg/hourglass/doc.go`, `api/openapi.yaml`, `ci.sh`, `tools/`, docs/decisions.md, and the RESULT.md files of tasks 21a (config schema, env vars), 30 and 32 (vsphere config and privileges), 31 (`check-provider`, `pkg/hourglass/server`), 33 (images), 34 (stacks), 38 (example and API awkwardness notes), 28 (build tag, binaries), 20 (auth behaviour).
## Contents
- `README.md`: what Hourglass is in three or four sentences (token model in one paragraph: weight x multiplier x time, bands, monthly allowance); status (v1, tested against a simulator, not yet run against a real vCenter); a quick start that works on a machine with Docker and Bazel: load images, start the bundled stack, open the UI, sign in as the local admin (where the password comes from, forced change), sign in as a realm user, approve them, acquire a setup; a second quick start with no Docker and no Bazel: `go build ./cmd/hourglassd` giving an API-only binary, run with a minimal config and the `static` provider; build and test commands (`bazel build //...`, `bazel test //...`, `./ci.sh`, `go build ./...`); repository layout table; links to the other docs, the spec and the license. Keep it to what a newcomer needs; no badges, no roadmap beyond the spec's out-of-scope list in two lines.
- `docs/extending.md`: the model (what the core does and does not know); each of the four interfaces with its exact Go declaration copied from `pkg/hourglass`, what the core guarantees when calling it (timeouts, concurrency, what failure does: e.g. a failing pressure source fails the poll and nobody is charged), and a minimal working example for each (compile-checked: put the examples in a throwaway module and build them, or point to the files under `examples/custom/` and quote from them); `Snapshot`, `HoldState`, `Decision` (weight 0 means "use the rate rules"; use `Snapshot.Time`, not the wall clock); registration and the config block each factory receives; building your own binary (`pkg/hourglass` + `pkg/hourglass/server`, importing the extensions you want, including a pressure source and a metering policy); the full event table (type, when it fires, vetoable, the JSON form with one real example payload produced by the code); delivery semantics (in-order queue, 30 s timeout, at most once, not retried, lost at shutdown, veto inside the request); the webhook hook (headers, signature verification snippet); the conformance suites and how to run them; `hourglassd check-provider`; the bundled extensions and their config keys.
- `docs/deploying.md`: bundled vs split mode and when to choose which; images and how they are built and loaded; the full configuration reference as a table (every file key and environment variable that exists in `internal/config`, default, meaning; and the admin settings that live in the database); OIDC setup against any IdP (redirect URL, scopes, PKCE, what the first sign-in looks like, approving users); the local admin account; TLS and cookies (the session cookie is always `Secure`: serve over HTTPS behind a proxy, `localhost` excepted); the vSphere provider and pressure source (config keys, read-only role, the privilege table from task 32, `check-provider`) including the spec's first-run checklist against a real vCenter reproduced as a checklist; seed file format and that it is applied once; shadow mode rollout (enforcement off for 2 to 4 weeks, then calibrate); backup with `VACUUM INTO` (a tested command line using the `sqlite3` CLI, and the note that the process is the only writer); metrics listener (never on the public port) and the metric names actually exported; logs; upgrade (migrations run at start); data retention (usage samples 13 months, deliveries 90 days); known limits (single instance, no HA).
- `CONTRIBUTING.md`: prerequisites and versions actually pinned; build and test; the rules that CI enforces and why (SPDX header in every source file, the core stays generic and what `tools/check_core_generic.sh` checks, permissive dependency licenses and the allowlist file, Gazelle up to date, generated UI API types in sync with `api/openapi.yaml`); how to add an API route (OpenAPI first, then handler, the contract and permissions tests will tell you what is missing); how to add a migration (new numbered file, never edit an old one); commit message convention (cite requirement ids); where decisions are recorded; how to run the end-to-end test (`e2e/run.sh`, if present; otherwise say it is being added); licence of contributions (MIT).
## Style
Plain, direct, second person for instructions. Short sentences. Tables for reference material, numbered lists for procedures, code blocks for anything typed. No marketing language, no emoji. Do not claim anything is production-ready or verified against a real vCenter.
## Scope
May write: `README.md`, `docs/extending.md`, `docs/deploying.md`, `CONTRIBUTING.md`, this task folder. Do not start Docker stacks (another agent is using the ports); you may run `go build`, the `hourglassd` binary on port 18180 with a temp database, `go doc`, and read anything. Do not edit `docs/SPEC.md`, `docs/progress.md` or `docs/decisions.md`.
