## Behaviour
`NewService(Deps)`: store, events dispatcher (interface with `Veto(ctx, Event) error` and `Emit(Event)`), poll view func, providerConfigured bool, clock.
- `Acquire(ctx, user, setupID) (Hold, error)`. Checks, in this order, each with its own typed error carrying a stable code: user has a role and is not the local admin (`forbidden`); setup exists (`not_found`), is enabled (`setup_disabled`) and free (`setup_held`); balance above zero unless enforcement is off (`insufficient_tokens`); active holds < `max_holds_per_user` (`hold_limit`); then `hold.acquiring` through `Veto` (`hook_veto`, with the hook's message). Then create the hold; the database's partial unique index is the final arbiter of a race (map to `setup_held`); emit `hold.acquired`. Events carry the user, the setup with labels and details, and the hold. Nothing is charged at acquire.
- `Release(ctx, actor, holdID, opts{Force bool, Reason string}) (Hold, error)`: the owner may release their own hold; an admin may release their own the same way, and may force-release any hold with a required non-blank reason (`validation` otherwise); anyone else gets `forbidden`; an already released or unknown hold is `not_found`. Non-forced release is refused with `still_deployed` ("This setup is still deployed. Tear it down, then release.") when `release_requires_teardown` is on, a provider is configured, the latest successful poll exists and reports the setup's resource name. With no provider, or the setting off, or no successful poll yet, release proceeds. Records `released_at`, `released_by`, `release_reason`; a force-release also writes an audit-log row in the same transaction; emit `hold.released` with `{"forced": bool, "reason": ...}`.
- Lowering the hold limit never releases anything (HOLD-5): only Acquire reads it.
## Tests
Every refusal in order; shadow mode lets a zero-balance user acquire (MET-6); limit 2 then third refused; limit lowered below current holds keeps holds and blocks new; veto by hook returns its message and creates nothing; veto timeout; two concurrent acquires of one setup: exactly one succeeds; local admin cannot acquire; release refused while reported, allowed after; force-release requires admin and reason, is audited; events order and content; -race.
