# 34 local stacks: compose (bundled and split), Keycloak realm, sample config, seed
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
`docker compose up` brings up a complete local Hourglass in each of the two modes with Keycloak and the simulator, healthy and usable from a browser on the host, with nothing needing a real vCenter. Spec: docs/SPEC.md "Testing without a vCenter" item 4, "v1 reference scenario" (the sample config and seed are exactly that table), UI-3, UI-4, AUTH-1, SET-7, Configuration. Decisions D8, D26, D29.
## Context
tasks/33-images/RESULT.md (image names, how to load them, the e2e variants and their clock control endpoint), tasks/33b-simulator-tool/RESULT.md (control API, credentials), tasks/21a-app-wiring/RESULT.md (config schema, env overrides, seed format), tasks/30-vsphere/RESULT.md (vsphere config block), tasks/20-auth/RESULT.md (OIDC settings, cookie rules).
## Deliverables (all under `deploy/`)
- `config.sample.yaml`: the reference scenario: provider `vsphere` (URL of the simulator service, `insecure_skip_verify: true` for the simulator's self-signed certificate, with a comment that real deployments set it false), pressure `vsphere` with the same connection block, metering `default` with `start_on_allocation: true`, `start_after: 2h`, hooks none, OIDC from environment. Secrets are never in the file: they come from environment variables in the compose files, and those are obviously fake development values (e.g. `dev-only-not-a-secret`), with a comment saying so.
- `seed.sample.yaml`: setups `lab-01` .. `lab-06` with `size` labels (two each of `medium`, `large`, `extralarge`), small neutral `details` blobs, rate rules `size=extralarge` -> 4, `size=large` -> 2, default weight 1. No proprietary data. The settings the scenario needs that are not seedable (resource name template `{{.SetupName}}_RP`, display label key `size`) are documented as first-run admin steps, and applied by the end-to-end test through the API; do not add seed features the spec does not have (SET-7 seeds setups and rate rules).
- `keycloak/realm-hourglass.json`: realm `hourglass`, one confidential client `hourglass` (authorization code flow, PKCE S256 required, redirect URI for the local stack, standard scopes), three users (`alice`, `bob`, `carol`) with email, first and last name and development passwords; no real names or addresses (`@example.com`). Imported at start with `--import-realm`. Pin the Keycloak image by version tag. Development mode (`start-dev`) is fine.
- `compose.bundled.yaml`: services `hourglass` (image `hourglass-e2e:dev` by default, overridable with an env var to the plain `hourglass:dev` image), `keycloak`, `vcsim`; a named volume for `/data`; healthchecks; `depends_on` with conditions so Hourglass starts after Keycloak discovery answers.
- `compose.split.yaml`: `hourglass-api` (`ui.serve: false`), `hourglass-ui` (proxying to it), `keycloak`, `vcsim`. The browser talks only to `hourglass-ui`.
- One origin and OIDC from both sides: the browser runs on the HOST at `http://localhost:8080` (Chromium accepts `Secure` cookies on `http://localhost`). The OIDC issuer URL must be identical for the browser and for the Hourglass container. Recommended: give Keycloak the hostname `keycloak.localhost` (browsers resolve `*.localhost` to loopback; add it as a network alias so containers resolve it to the Keycloak container), run Keycloak on the same port inside and outside (e.g. 8081:8081 with `KC_HTTP_PORT=8081`, `KC_HOSTNAME` set accordingly), issuer `http://keycloak.localhost:8081/realms/hourglass`. If that does not work on Docker Desktop for macOS, find another arrangement that keeps a single issuer URL without TLS, and document it.
- Ports published to the host: app 8080; Keycloak 8081; simulator control 8990 (the SOAP port need not be published); e2e clock control 8091. The two stacks use the same host ports and distinct project names, so only one runs at a time.
- `deploy/README.md`: how to load images, start and stop each mode, the sign-in details (local admin password comes from the compose env and must be changed at first sign-in), and the three realm users.
- `deploy/smoke.sh <bundled|split>`: loads images, `docker compose up -d --wait`, then checks with curl: `/healthz` 200; `/` returns the UI's HTML; `/api/v1/auth/methods` reports OIDC available; `GET /auth/oidc/start` redirects to the issuer; Keycloak discovery reachable at the issuer URL from the host and from inside the Hourglass container; the simulator control endpoint answers; local admin can sign in through `POST /auth/local` with the compose password (cookie received); after the first successful poll `GET /api/v1/admin/collector` (as admin, after the forced password change) shows provider `vsphere`, pressure source `vsphere`, last poll OK, and the six seeded setups exist. Then `docker compose down -v`. Exit non-zero on any failure, always tearing down.
