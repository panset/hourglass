# 19 api/openapi.yaml
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
`api/openapi.yaml` (OpenAPI 3.0.3): the complete UI-to-backend contract for every route in docs/SPEC.md "HTTP API", detailed enough that a UI can be built from it and Go handlers validated against it (UI-2). No Go code in this task.
## Sources
docs/SPEC.md sections "HTTP API", "Roles and permissions", AUTH-1..8, SET-*, RULE-*, HOLD-*, MET-*, LED-*, ADM-*, UI-5, "Dashboard pages" (every number a page shows must come from some response) and `docs/ui-notes.md` (the wireframes: every column and field shown there needs a source field). Settings JSON form: `.orchestrator/hourglass-v1/tasks/16b-settings/BRIEF.md`. Event names: the spec's event table.
## Requirements
- Exactly the routes of the spec's HTTP API table, no more: the two OIDC routes, `POST /auth/local`, `POST /auth/local/password`, `POST /auth/logout`, `GET /healthz`, `GET /api/v1/auth/methods`, `GET /api/v1/session`, `/api/v1/me`, `/me/holds`, `/me/ledger`, `/me/usage`, `/pressure`, `/setups`, `/setups/{id}/acquire`, `/holds/{id}/release`, admin users (list with `status` filter, `PUT roles`, `POST reject`, `POST grants`, `POST reset`), admin setups (`POST /admin/setups`, `PUT` and `DELETE /admin/setups/{id}`), `GET`/`PUT /admin/rules`, `GET`/`PUT /admin/settings`, `GET /admin/collector`, `GET /admin/audit`. Where a page needs data that no listed route obviously carries (orphans, outage history, event delivery errors, pending count for the navigation, month-to-date burn, admin-only setup fields, force-release reason), put it in the response or request of the listed route the spec assigns it to (e.g. orphans and outages in `/admin/collector`; force-release is `POST /holds/{id}/release` with `{"force": true, "reason": "..."}` for admins; pending count in the admin users list response) and say so in the description. If something truly has no home, do not invent a route: list it in RESULT.md as an open question.
- Every operation: `operationId` (camelCase, unique), a tag, summary, `x-roles` (one of `public`, `session`, `role`, `admin`, `local-admin`) matching the spec's "Who" column, `x-csrf: true` on state-changing operations, request body schema, all success and error responses.
- One error schema everywhere: `{"error": {"code": "...", "message": "..."}}`. Define the enum of codes with the HTTP status each maps to, at least: `unauthenticated` 401, `no_role` 403, `forbidden` 403, `csrf` 403, `password_change_required` 403, `not_found` 404, `validation` 400 (with optional `field`), `invalid_selector` 400, `insufficient_tokens` 409, `hold_limit` 409, `setup_held` 409, `setup_disabled` 409, `still_deployed` 409, `hook_veto` 409, `has_active_hold` 409, `last_admin`/`self_demote` 409, `local_admin_protected` 409, `conflict` 409, `rate_limited` 429, `internal` 500.
- Amounts: tokens as JSON numbers with up to three decimals (the API converts from milli-tokens); name fields `..._tokens`. Timestamps RFC 3339 UTC strings. Ids are integers. Periods `YYYY-MM`.
- Schemas of note: `Session` (user id, username, email, name, auth_source, status, roles array possibly empty, csrf_token, must_change_password, `is_local_admin`; for an unassigned user exactly this and nothing else: AUTH-5); `Me` (balance, burn per hour now, projected run-out or null, hold count and limit, allowance, enforcement flag; local admin has `balance_tokens: null`); `Hold`; `LedgerEntry`; `UsageDay`; `Pressure` (raw, smoothed, multiplier, bands, source name, 7-day history points); `Setup` (id, name, labels, weight, state `free|held|disabled`, holder with name and balance, held_since, deployed, metering, cost_per_hour_tokens now and at the highest band, details JSON; admin-only fields in a nullable `admin` sub-object: enabled, resource_name, resource_name_override, last_seen_at, matched_rule_selector); the setups list response also carries `display_label_keys`; `AdminUser` (roles, status, balance, month-to-date burn, active holds, first sign-in time, last login, is_local_admin); `Rule` and the rules response (ordered rules each with `match_count`, `default_weight`, `unmatched_setups`); `Settings` plus a read-only `runtime` block in the GET response (provider, pressure source, metering policy, hooks, OIDC issuer, timezone: names only, never secrets); `Collector` (active extension names, last successful poll, last error, recent runs, outages, orphans, recent failed event deliveries, queue length); `AuditEntry` with actor/action filters and limit/offset paging.
- Security scheme: cookie session (`apiKey` in cookie) plus the `X-CSRF-Token` header parameter on state-changing operations.
- First line of the file: `# SPDX-License-Identifier: MIT`. Neutral examples only (`tier: a`, `lab-01`), no real names, no vSphere-specific wording.
