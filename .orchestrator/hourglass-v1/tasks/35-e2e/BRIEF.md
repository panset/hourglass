# 35 end-to-end acceptance test in a headless browser, bundled and split
Job intent: .orchestrator/hourglass-v1/INTENT.md (read it first). Rules: .orchestrator/hourglass-v1/CONTRACT.md.
## Goal
A scripted test that drives the real UI in a headless browser through the spec's acceptance path, once against the bundled stack and once against the split stack. Spec: docs/SPEC.md "Testing without a vCenter" item 4 and the "Acceptance path" paragraph, quoted here as the checklist:
1. a new user signs in and sees the not-authorized page;
2. the local `admin` approves them;
3. they acquire a `size=large` setup;
4. a resource pool is created in the simulator and metering starts at weight 2;
5. pressure is driven across a band and the debit rate changes;
6. a third acquire is refused by the hold limit;
7. release is refused while the pool exists and succeeds after it is destroyed;
8. the month is rolled over with a negative balance and the debt carries.
## Context
tasks/34-compose/RESULT.md and `deploy/README.md` (stacks, ports, users, how to start), tasks/33-images/RESULT.md (e2e clock control), tasks/33b-simulator-tool/RESULT.md (pool and pressure control API), `docs/ui-notes.md` and the page sources under `ui/src/pages/` (labels to click), decisions D8, D12, D19, D22, D29 in docs/decisions.md (how charging and smoothing behave: charging starts the poll after metering starts; pressure is a 15-minute average; a clock jump is an uncharged outage and triggers the rollover).
## Design
- Playwright (`@playwright/test`, Chromium only) in `e2e/browser/` with its own `package.json` and lockfile; browsers installed by `npx playwright install chromium`. It is NOT part of `bazel test //...` (it needs Docker): exclude `e2e/browser` from Bazel (`.bazelignore`) and provide `e2e/run.sh <bundled|split|both>` that loads images, starts the stack, runs the test, collects the Playwright report and container logs into `e2e/out/` (git-ignored), and always tears the stack down. Exit code reflects the test.
- Every step acts through the browser UI as a user would (sign in through Keycloak's login form as `alice`; local admin signs in through the admin form and completes the forced password change; approval, acquire, release, settings edits are clicks and form fills). Only two things are driven outside the UI, because they stand in for the outside world: the simulator control API (create/destroy the pool `<setup>_RP`, set pressure) and the e2e clock control (month jump). Reading numbers for assertions is done from what the UI shows; an API read through the browser session is acceptable only to wait for a poll to land.
- Admin first-run steps through the Settings page: resource name template `{{.SetupName}}_RP`, display label key `size`, enforcement ON (so the balance rule is live), and for speed pressure bands that put the simulator's baseline in one band and the driven value in another. Poll interval stays at its 1-minute minimum; wait for polls by polling the page/API with generous timeouts rather than fixed sleeps. Because pressure is a 15-minute average, choose band thresholds and driven values so that one or two polls after the change the smoothed value is in the new band; compute this in the test from the pressure shown, do not guess.
- Assertions, by step: (1) the exact sentence "You are not authorized to use Hourglass. Reach out to your admin." and that no navigation or data is shown; a direct API call from that browser session to `/api/v1/setups` returns 403 `no_role`. (2) alice appears under pending requests with her email; after approval she lands on My usage with a balance of 300. (3) the acquire dialog shows a cost per hour; the setup shows as held by alice, not yet metering. (4) after the pool is created and a poll runs, the hold shows deployed and metering, weight 2; after the next poll the balance has dropped by weight 2 x multiplier x elapsed, within a tolerance of one poll. (5) after driving pressure across a band the multiplier shown in the top bar changes and the per-poll debit changes in the same ratio (compare two consecutive debits before and after, from the ledger history on My usage). (6) with two setups held, a third acquire is refused with the hold-limit message. (7) Release shows "This setup is still deployed. Tear it down, then release."; after destroying the pool and one poll, Release succeeds and the setup is free. (8) make the balance negative (the admin grants a negative amount with a reason through the Users page, or let debits do it), advance the clock past the month boundary via the clock control, wait for a poll, and assert the new month's opening shows allowance minus the debt (ledger shows carry-over and allowance entries, balance = 300 - debt minus any debits since).
- The same spec file runs for both modes; only the compose file differs. In split mode additionally assert that the page and the API are served by different containers (e.g. a response header or the UI container's `/ui-healthz`) while the browser origin is one.
- Robustness: unique screenshots and a trace on failure; no test depends on a previous run's data (fresh volume each run); total time per mode stated in RESULT.md.
## Scope
May write: `e2e/browser/`, `e2e/run.sh`, `.bazelignore`, `.gitignore` (for `e2e/out`, `node_modules`, Playwright artifacts), `tools/check_spdx.sh` (to cover or skip the new files correctly), this task folder. If a product bug blocks a step, do not patch product code or weaken the assertion: record the exact failure (step, expected, actual, logs) and continue with the remaining steps where possible, then report `partial` with the list. Small test-id attributes in `ui/src` are allowed only if a control truly cannot be located by role or label, and must be listed.
## Long-running steps
Each mode takes roughly 10 to 20 minutes because polls are one minute apart. Run each mode with a 30-minute limit, output to a log, read the tail. Playwright browser download: allow 5 minutes.
## Done when
`e2e/run.sh both` exits 0 on this machine, or the task is `partial` with a precise list of failing steps and causes. RESULT.md has, per mode, a step table (pass/fail, what was asserted, observed values) and the run time.
