## Parts
1. `cmd/hourglass-ui`: a small Go binary for split mode that serves the built UI with `internal/uiserve` (embedded under the `ui` tag, same mechanism as hourglassd) and reverse-proxies `/api/`, `/auth/` and `/healthz` to the API container (`-api http://host:port` or `HOURGLASS_UI_API`), preserving the Host seen by the browser (`X-Forwarded-Host`/`-Proto` set, cookies and `Set-Cookie` untouched, redirects from `/auth/*` passed through unmodified) so the browser sees one origin (UI-4). Its own `/ui-healthz`. Tests with `httptest`: static file, SPA fallback, proxying of the three prefixes including a 302 with `Set-Cookie`, nothing else proxied, upstream down gives 502 JSON in the standard error shape.
2. `hourglass.Options.Clock`: an additive, optional field (`interface{ Now() time.Time }`, nil = wall clock) passed through `internal/app` to every component that takes a clock (collector, ledger service, holds, auth sessions, events). Test that a supplied clock is the one the collector and ledger see. Generic: no test wording in product code.
3. `e2e/hourglassd-e2e`: a test-only main identical in behaviour to `cmd/hourglassd` (same extension imports, same subcommands) plus a clock with an adjustable offset: it serves a tiny control endpoint on a separate address given by `HOURGLASS_E2E_CONTROL` (e.g. `:8091`): `GET /clock` and `PUT /clock {"offset": "720h"}` (offset added to the wall clock from then on). Built in bundled (with UI) and API-only variants like the real binary. Nothing under `cmd/`, `internal/` or `pkg/` may import anything from `e2e/`.
4. Images with `rules_oci` (bzlmod; base `gcr.io/distroless/static-debian12:nonroot` pinned by digest via `oci.pull` for `linux/amd64` and `linux/arm64`): `hourglass` (hourglassd with UI), `hourglass-api` (without UI), `hourglass-ui` (the proxy binary with UI), and for the test stacks `hourglass-e2e`, `hourglass-api-e2e`, `hourglass-vcsim` (from `//e2e/simulator`). Binaries cross-compiled for Linux by rules_go platform transitions (pure Go, cgo off); user nonroot (65532); `WORKDIR /data`; `EXPOSE`-equivalent labels; entrypoint the binary; `/data` usable as a volume by the nonroot user (document the ownership requirement). Put the image targets in `deploy/images/BUILD.bazel` (or next to each binary; say which). Each image has an `oci_load` target tagged `manual` so `bazel run //deploy/images:load_hourglass` (etc.) loads `hourglass:dev` (etc.) into the local Docker daemon for the host architecture; `bazel build //...` builds the image layers without needing Docker.
5. A script `deploy/load-images.sh` that loads all images needed by the stacks, and a smoke check (script, run by hand and by the later end-to-end task, not by `bazel test`): load `hourglass:dev`, `docker run` it with a temp volume and `HOURGLASS_ADMIN_PASSWORD` set to a throwaway value, wait for `/healthz` 200 and that `/` serves HTML, confirm the process runs as non-root, then remove the container. Same for `hourglass-api:dev` (`/` is 404) and `hourglass-ui:dev` pointed at it.
